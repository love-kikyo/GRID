## 正式任务的最小记录

资源约定（2026-09-16 作者确认）：**整个作业最多 4 个 CPU 核，不是每张 GPU 4 核**。当前 3-GPU 正式训练采用 3 tasks × 1 CPU，显式绑定 CPU；线程池设为 1、训练 worker 每 rank 1，validation / test worker 暂不改。检查实际 AllocCPUS 和所有 rank / 子进程的 affinity，不以 worker 数替代 CPU 配额。短测 / 导出 / 分析也受此上限约束，未适配的旧入口不得直接沿用原资源申请。

提交前记录：方法、seed、启动命令 / 参数、代码 commit 与 dirty 状态、数据协议、初始化 checkpoint、训练 preflight 路径。提交后立即登记 job ID 与 run 目录。

任务结束后记录：Slurm 状态和退出码、失败原因或 best checkpoint、选优 / 评估口径、原始日志位置。`COMPLETED` 需要结合脚本用途解释；测试配置打印不算训练结果。

训练过程中不要改动该任务依赖的源码；确需并行开发时使用独立工作副本 / worktree，并为各任务绑定独立版本。不能改旧 preflight 来掩盖代码漂移。

## 默认任务提交节奏（2026-09-21 作者更新）

- **长任务**（训练、全量 test 等）：仍最多保留 **1 个运行 + 1 个通过依赖等待的后继**；更后面的任务等验收后再安排，不预排整条长任务链。
- **已知短任务**（validation、选权及配套验收）：作者允许一次提交多项。本轮按 `afterok` 串行串接，整个链同时最多一个作业执行；不是放宽整项 4 CPU 限制，也不是授权批量长任务。
- 自动推进须把产物验收作为成功退出的必要条件；单个阶段采用“前置绑定 → 全量 validation → 产物验收 → 固定网格选权 → 独立复算”，全部通过才放行后继。`set -euo pipefail`、`afterok` 与 `--kill-on-invalid-dep=yes` 共同阻止失败后继续，不把 Slurm 的 0 退出码当作验收替代。
- 长短按同类任务的实测耗时判断，不按 launcher 的最长 walltime 判断。当前 validation 实测约 8–14 分钟，选权 / 验收约一分钟；全量 test 约一小时，仍按长任务管理。
- 取消但从未启动的 job 保留 CANCELLED 记录，不记作训练失败或实验结果；重新提交使用新 job ID，记录替代关系，不改写原提交历史。
- 只读状态检查与文档维护可继续；新的并发规模或其他例外须由作者确认。09-11 的“1 + 1”约定继续约束长任务，短任务例外自本次更新生效。

- `CURRENT_STATUS_ZH.md`：短摘要、核验时间、当前一个优先事项；覆盖旧状态，不追加长篇日志。
- `RUN_LEDGER_ZH.md`：job 与指标的唯一台账；每次状态变化更新对应行，链接原始产物。
